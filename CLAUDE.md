# SmartSKU - умные ящики для хранения мелкого крепежа и фурнитуры

**Идея:** мы разрабатываем прототип умных ящиков для прозрачного учёта использования мелких весовых комплектующих на участках сборки. Каждый ящик будет снабжён тензодатчиком, настроенным на тару и измеряющим вес внутри него. Также во время калибровки узнаётся вес одного компонента, что позволяет пересчитывать массу в количество.

## Детали модульного физического устройства блоков хранения
На этапе прототипа мы хотим сделать унифицированные боксы, состоящие из 4х умных ячеек. Боксы могут подсоединяться друг к другу в произвольных конфигурациях (слева, справа, сверху, снизу), расширяя вместимость всей конструкции. 

### Устройство одного бокса
1. Все боксы независимы друг от друга.
2. Внутри бокса управлением занимается ESP32, куда подключаются датчики и прочие компоненты умных ячеек. ESP32 передаёт информацию по wi-fi на бэкенд сервер и так же получает команды.

#### Устройство одной умной ячейки
1. Тензодатчик, измеряющий массу.
2. NFC метка на ячейке и NFC считыватель прикреплённый к стенке бокса. Наличие NFC позволяет менять ячейки местами, но сохранять инфомрацию о калибровке, поскольку тензодатчики расположены в корпусе бокса.
3. Одноцветный дисплей для отображения цифр.

Код для управления ESP пишется отдельным человеком в .ino файлах, этот репозиторий посвящен исключительно software части. В дальнейшем мы добавим код управления ESP. 

## Верхнеуровневые идеи работы

### Инициализация бокса
Предполагаем, что пользователь купил новый бокс и хочет приконнектить его к уже существующей системе боксов или же это первый бокс. Для этого должен быть реализован некоторый протокол инициализации, при котором новый бокс получит уникальный id: `box_id` от нашего бэкенд сервиса. Общение должно происходить через wi-fi.

#### Информация, посылаемая боксом
Мы накидали примерный контракт сообщения, который бокс будет постоянно отправлять с настраиваемой периодичностью, например раз в полсекунды `json_contracts/box_data.json`. Здесь:
- `box_id`: уникальный идентификатор бокса, который присылает сообщение
- `locker_id`: позиция умного ящика в структуре бокса
- `nfc_flag`: флаг, показывающий подключён ли nfc тэг к считывателю. Служит индикатором вставлена ячейка в бокс или нет
- `nfc_id`: уникальный идентификатор ячейки через nfc метку
- `weight`: показания тензодатчика
- `piece_weight`: масса одного элемента после процесса *калибровки*
- `number_of_pieces`: математически посчитанное число компонентов

### Калибровка
Чтобы система понимала какие именно компоненты будут хранится в определённой ячейки, необходим процесс калибровки. Он состоит из следующих шагов:
1. Пользователь нажимает в приложении кнопку калибровка
2. На фронте отображаются свободные ячейки в боксах
3. Пользователь выбирает ячейку (мы получаем информацию о `box_id` и `locker_id`) и пишет названия компонетов, которые он туда кладёт + тэги для удобства поиска потом
4. Отображается сообщение: "Положите в выбранную ячейку калибровочное число компонентов" и появляется окно для ввода этого количества (получаем число `num_of_pieces`)
5. После этого оптравляется json с командой для калибровки на ESP по контракту `json_contracts/calibration_command.json`
6. Пользователь подходит, высовывает ячейку (`nfc_tag` = false), насыпает туда `num_of_pieces` компонентов, засовывает обратно (`nfc_tag` = true + обновленные показания тензодатчика). ESP под капотом всё это пересчитывает и начинает присылать обычные сообщения. (До калибровки значения `piece_weight` и `number_of_pieces` какие-то заглушки)

### Сообщения для дисплеев
Каждая ячейка при изменении информации о её содержимом должна получать команду для дисплея в формате `json_contracts/indicators_command.json`, где
- `box_id`, `locker_id`: идентификаторы положения ячейки
- `screen_number`: число для отображения на дисплее
- `screen_mode`: `count` (количество), `take` / `put` (сборка: `t N` / `P N`) или `off` (погашен)

### Обычный сценарий работы
Пользователь подходит к стенду и достаёт ячейку для работы (`nfc_tag` = false). Он может унести её с собой, или сразу досыпать/взять компонентов и засунуть обратно. Все эти изменения должны логгироваться на бэкенде для последующего учёта. + посылаться соответствующие сигналы на индикаторы.

**Система должна поддерживать нативную интеграцию с другими сценариями работы, завязанными на действия в приложении**


# Software реализация

Я вижу микросервисную реализацию:
1. бэкенд сервер, который пока локально поднимается на компьютере. Язык программирования python, фреймворк FastAPI, пакетный менеджер uv.
2. фронтенд сервис для взаимодействия с пользователем. Для начала можно начать с вебприложения, которое тоже хостится локально на компьютере, затем добавим приложения для android и ios. По дизайну будем обсуждать позже

## Правила напсиания кода
1. Только ООП и конфиги. Никаких висячих функций и глобальных переменных
2. Конфиги в .yaml файлах
3. Инъекция зависимомтей через dishka
4. Для инференса упаковывай всё в docker
5. Пиши в `README.md` краткое описание архиктектуры приложений, чтобы прочитав этот файл в новой сессии можно было сразу понять, что происходит и на каком этапе находимся.
6. Линтер ruff: после любых изменений кода прогоняй `uv run ruff format . && uv run ruff check --fix .` в каждом затронутом проекте (`backend/`, `emulator/`). Для `frontend/` — `npm run build` (проверка типов tsc + сборка)

## Идея для обдумывания
Для тестирования всего приложения я бы не подключался к реальным ESP пока. Может можно написать какой-то простенький сервис с ручками, который будет эмулировать поведение - слать постоянно json сообщения как ESP, и можно будет вытащить ящик, изменить вес и тд.
